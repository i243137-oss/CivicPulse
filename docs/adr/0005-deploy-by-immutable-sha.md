# ADR 0005: Immutable Deployment via Git Commit SHA Tagging (Deploy-by-SHA)

## Status
**Accepted**

## Context
Deploying software into multi-replica Kubernetes clusters or Docker Compose production environments requires deterministic guarantees regarding what code is currently executing. 

A common operational anti-pattern is deploying images tagged with `:latest` or mutable branch names (e.g. `:main` or `:dev`). Using mutable tags causes critical reliability and security hazards:
1. **Non-Deterministic Rollouts**: Different nodes or pod replicas pulling `:latest` at different times can pull distinct image layers, leading to split-brain runtime behavior across pods within the same Deployment.
2. **Broken Rollback Guarantees**: Running `kubectl rollout undo` or redeploying an earlier manifest does not guarantee a return to the previous state if `:latest` on the container registry has already been overwritten.
3. **Audit and Compliance Gaps**: It becomes impossible to trace a running container back to the exact source commit, CI pipeline run, or Software Bill of Materials (SBOM).
4. **Cache Poisoning**: Local container engine caches may refuse to pull updated layers if the tag has not changed, resulting in stale container execution.

## Decision
We enforce an **immutable deploy-by-SHA** strategy across all Continuous Integration, Continuous Delivery, and production deployment environments:

1. **Immutable Tag Generation**:
   - Container images built in CI/CD (`.github/workflows/cd.yml`) are tagged with the full Git commit SHA (`${{ github.sha }}`) and semantic version tags (`v*.*.*`).
   - The `:latest` tag is optionally pushed solely for developer image discovery on GitHub Container Registry (GHCR), but is **strictly forbidden** from being referenced in any Kubernetes deployment manifest or production Compose file.

2. **Declarative Kustomize Overlays**:
   - Manifests in `infra/k8s/overlays/prod/` pin images using Kustomize `images:` transformations targeting the immutable commit SHA:
     ```yaml
     images:
       - name: civicpulse-backend
         newName: ghcr.io/i243137-oss/civicpulse-backend
         newTag: 30585980a044cf2978601e365f6d97509193bda4
     ```
   - Production Docker Compose files (`compose.prod.yaml` and `docker-compose.prod.yml`) mandate `${IMAGE_TAG}` with fallback to immutable semantic versioning (`v1.0.0`), rejecting `:latest`.

3. **Software Bill of Materials (SBOM) Traceability**:
   - Every published container image digest is paired with an SPDX-JSON SBOM generated by Syft (`anchore/sbom-action@v0`). The SBOM file name includes the Git commit SHA, creating an unbroken cryptographic audit trail from source commit $\to$ image hash $\to$ vulnerability scan $\to$ deployed pod.

4. **Rollback Determinism**:
   - Imperative rollbacks (`kubectl rollout undo deployment/backend`) instantly revert to the previous ReplicaSet, which points to the prior immutable commit SHA.
   - Declarative rollbacks are executed by reverting the Git commit or updating the Kustomize `newTag` to the previous SHA, ensuring Git remains the single source of truth.

## Consequences

### Positive
- **100% Traceability**: Every running container in production maps directly to a specific Git commit SHA and CI pipeline run.
- **Atomic, Deterministic Rollouts**: All replicas in a Deployment pull the exact same image layers regardless of node scheduling time.
- **Instant, Reliable Rollback**: Rollbacks are deterministic because previous images on GHCR are immutable and never deleted or overwritten.
- **Security Compliance**: Mechanical pre-submission checker (`scripts/check_submission.py`) automatically audits all manifests to ensure zero `:latest` references exist.

### Negative / Trade-offs
- Deployment scripts must inject or substitute the commit SHA into deployment manifests dynamically during the CD pipeline.
- Container registry storage usage increases over time because old SHA-tagged images are preserved (mitigated by automated GHCR retention policies).
